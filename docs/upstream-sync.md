# 内核来源与同步

## 当前实现

任务内核固定为 `@juicesharp/rpiv-todo@2.15.0`，提交 `ce6d3530410812ca504ec294995581a52170f9e1`。`UPSTREAM.json` 是来源清单：顶层 upstream 是当前内核 pin，initialUpstream 保留初始提取版本；每个导入文件使用自己的 commit，未注明时使用 importStatus.defaultCommit。

`importStatus.kernelFiles` 列出的 11 个文件保留上游原字节，包括 `.ts` 导入路径。它们负责类型/schema、参数归一化、状态转移、依赖图、会话状态、快照恢复、文本清理和结果 envelope。`npm run test:pack` 检查这些文件的 SHA-256 和提交均与当前 pin 一致。工具注册和生命周期由本扩展衔接，Kimi-style widget、详情页、配置及主题仍由本扩展维护。

`rpiv-todo-state` 只是写进 Pi 会话分支的 custom entry 类型，不是独立 npm 包、共享内核服务或可订阅的同步 API。相同标识让新旧扩展读懂同一类历史快照，不会让两个实现的代码自动更新。新旧 TODO 扩展仍不能同时启用。

扩展运行时不会检查版本、下载源码或自动替换内核。构建和运行不依赖另一份已安装的 rpiv-todo，也不会执行其扩展入口。

## 能否自动跟随上游

可以做**开发阶段的自动升级**，不宜做无校验的运行时跟随。已审计的 2.15.0 包只分发扩展源码，没有独立 core 包、包级 exports/main 或文档化的稳定内核入口。

| 方式 | 作用与限制 |
| --- | --- |
| 固定来源 + 自动检测／升级 PR | 推荐的近期方式。保留可重现安装，让 CI 在合入前验证兼容性；工具注册等桥接层仍需审查。 |
| 直接依赖 rpiv-todo 的内部文件 | 当前文件可以被定位，但不是稳定承诺。内部路径、状态单例和宿主模块加载方式都可能变化；依赖升级也需要锁文件及测试，不能保证自动兼容。 |
| 上游抽出独立 core 或提供关闭原 widget 的公开 API | 更适合长期复用。由同一个内核拥有工具、会话状态和持久化，显示层只消费状态，不重复注册 todo。需要上游提供并维护这个边界。 |

仅让两个扩展一起加载，再删除原扩展的私有 widget key，不是可靠的 UI 适配接口：事件顺序、延迟加载和内部 key 都可能变化。

## 自动升级流程应守住的边界

以下是可实施的维护流程，**本仓库尚未配置定时检查、升级 PR 或自动合并**：

1. 查询 npm 发布版本，解析其固定 gitHead。下载对应 tarball，核对 registry 的 SHA-512，并核对固定 Git 提交的 package version、license 和所选文件。
2. 只处理白名单中的内核与相应回归测试；更新前确认本地文件仍匹配旧 pin 的哈希。不要覆盖尚未审查的本地内核修改，也不要复制整个 monorepo。
3. 生成来源清单、必要的锁文件及文档改动。保留每个文件的真实来源；不把仍来自旧提交的 UI/helper 记录成新来源。
4. 对比上游 `todo.ts`、`index.ts` 等衔接代码。参数归一化 hook、guidance、持久化调用或生命周期变更不能靠复制纯内核自动补齐；出现这些差异时应停下自动合并并要求审查。
5. 执行 `npm run verify` 和 `npm run test:tui`，覆盖批量原子性、错误参数、旧快照、坏快照、nested/codemode、分支与会话隔离，以及安装后的真实终端。
6. 以可审查的 PR 交付，不自动发布或改用户配置。通过验证也只说明已测环境兼容，不保证未来上游版本或所有扩展组合。

任何升级都保留 `todo` 和 `rpiv-todo-state` 的身份，除非另外设计并验证了显式迁移。依赖保持精确版本；不通过浮动依赖跳过验证。

## 稳定共享内核需要提供什么

长期直接复用需要的不只是 reducer：schema、参数归一化、结果 envelope、guidance、branch replay、nested 持久化及会话隔离也必须有明确契约。上游还需提供可供独立 UI 消费的状态读取／变更通知，并允许不注册原 widget。

具备这些接口后，本扩展可以缩减为显示适配层；现在保持固定的逐文件来源和完整兼容测试，更容易发现遗漏，也更容易回退。
